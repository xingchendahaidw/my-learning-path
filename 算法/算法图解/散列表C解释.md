关键设计解释
1. 整体结构：数组 + 链表
text

buckets[]  ┌──────┐
 index 0   │ NULL │
 index 1   │  ●───┼──→ (apple:0) ──→ (grape:60) ──→ NULL
 index 2   │ NULL │
   ...     │ ...  │

    buckets 是一个指针数组，长度 capacity。

    每个桶挂着一条单链表，存放所有哈希到该桶的元素。

    这就是经典的链地址法（separate chaining），冲突元素不抢别人的位置。

2. 哈希函数：为什么选 FNV-1a
c

h ^= *s++;  h *= 0x100000001b3;

    先异或再乘一个大质数，让每个字节都影响最终结果的高低位；

    分布均匀、实现极短、无需取模之外的开销；

    比 h = h*31 + c（Java 字符串那种）在短字符串上雪崩性更好。

% capacity 把 64 位哈希压到桶下标。这里 capacity 保持 2 的幂，理论上可用 & (capacity-1) 更快，但 % 更通用（以后若要改成质数容量也不用改代码）。
3. 冲突处理：链地址法 vs 开放寻址
	链地址法（本实现）	开放寻址（线性探测等）
冲突	挂到链表上	往后找空槽
装填因子	可以 > 1	必须 < 1
删除	直接摘链，简单	需要墓碑标记，麻烦
缓存友好性	差（指针跳转）	好（连续内存）
实现难度	低	中

对一般用途（尤其是需要频繁删除），链地址法是更稳妥的默认选择。
4. 装填因子与扩容
c

if ((double)(m->size + 1) / m->capacity > LOAD_FACTOR)
    hm_resize(m, m->capacity * 2);

    装填因子 size / capacity 衡量桶的平均链长。它越大，链表越长，查找越慢。

    0.75 是经验值：再高冲突明显变多，再低浪费空间。

    扩容时容量翻倍，把所有节点重新哈希到新桶（rehash）。这是 O(n) 操作，但由于容量翻倍，平均每插入一个元素只摊还 O(1)。

    注意：扩容后必须用新容量重算 idx，代码里显式重算了。

5. 内存管理细节

    key 被复制：hm_put 里用 dup_str 复制 key。这样调用者的字符串可以是栈上的、临时的，表内部自己持有所有权。删除/销毁时由表 free(e->key)。

    删除用二级指针：Entry **pp 指向"指向当前节点的指针"，这样删头节点和删中间节点用同一段代码，不需要特判前驱。

    销毁要遍历所有桶：只 free(buckets) 会泄漏所有节点和 key。

    返回值检查：malloc 失败返回 -1，调用方应处理。

6. 复杂度
操作	平均	最坏
put	O(1)	O(n)（全部冲突）
get	O(1)	O(n)
remove	O(1)	O(n)
扩容	摊还 O(1)	—

最坏情况出现在哈希函数极差、所有 key 落到同一桶时。实际使用好的哈希函数后基本不会发生。
可继续改进的方向

    通用 key：目前 key 固定为 char*。可以改成 void* + size + 用户提供的 hash/eq 回调，做成泛型哈希表。

    缩容：删除较多元素后可缩容一半，避免长期占用大数组。

    线程安全：加读写锁或分段锁（如 Java 的 ConcurrentHashMap）。

    用位运算取模：既然容量是 2 的幂，hash & (cap-1) 比 % 快一点。

    开放寻址版本：对性能敏感且不需要频繁删除的场景，可换成 Robin Hood 或 Swiss Table 风格。

    有序遍历：若需要按 key 顺序遍历，可在桶内换用红黑树（这就是 Java 8 HashMap 的树化策略）。
